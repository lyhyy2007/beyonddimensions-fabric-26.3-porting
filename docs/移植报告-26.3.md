## 2. 构建环境与复现步骤

```bash
# 依赖：JDK 25（工具链）、Gradle 9.5.1（wrapper 自带）
cd BeyondDimensions-26.3-Porting
gradlew.bat build          # 产物 build/libs/beyonddimensions-0.7.13+26.3.jar
gradlew.bat runServer      # 本地测试服务端
gradlew.bat runClient      # 本地测试客户端
```

`gradle.properties` 钉选：

```properties
minecraft_version=26.3
loader_version=0.19.5
loom_version=1.17.21
fabric_api_version=0.161.0+26.3
```

### 2.1 环境坑（本次实际踩到并解决）

1. **Gradle 发行版下载 PKIX 失败**：`services.gradle.org` 的重定向目标 `downloads.gradle.org` 证书链在 JDK 信任库里验证失败（`maven.fabricmc.net` / `repo.maven.apache.org` / `piston-*.mojang.com` 均正常）。解决：用 PowerShell（走 Windows 证书库）下载 `gradle-9.5.1-bin.zip`，解压进 `~/.gradle/wrapper/dists/gradle-9.5.1-bin/<hash>/` 并补 `.ok` 标记。
2. **TinyPinyin 依赖**：`com.github.promeg:tinypinyin:2.0.3` 不在 Maven Central，改用阿里云 public 镜像；Fabric 侧用 loom 的 `include`（Jar-in-Jar）替代上游的 `jarJar`。
3. **LWJGL 未进编译类路径**：上游直接使用 `org.lwjgl.glfw.GLFW` 键码常量，loom 26.x 不传递 LWJGL，需显式 `compileOnly "org.lwjgl:lwjgl-glfw:3.3.3"`。
4. **Access Widener 命名空间必须是 `official`**：26.x 不再混淆，写 `named` 会直接构建失败（`Expected official namespace for access widener entry, found: named`）。

## 4. 核心设计：加载器层全量原生化（无垫片）

### 4.0 演进过程与动机

第一版移植采用「在 `net.neoforged.*` 包名下重新实现 NeoForge API 面」的垫片方案（78 类 / 3407 行），好处是 221 个上游文件零 import 改写。但该方案有一个致命性质：**垫片类与真实生态库同名**。Fabric Loader 把模组 jar 依次放进 classpath，**先出现者胜**，且**不产生任何重复类告警**。

在真实整合包（140 个模组）中因此发生了类遮蔽（class shadowing）事故：

- 垫片的 `net.neoforged.fml.config.ModConfig$Type` 顶掉了 ForgeConfigAPIPort 的同名类；
- Puzzles Lib 的 `FabricConfigHolderImpl.<init>` 里对 `ModConfig$Type.extension()` 是**硬引用**（`invokevirtual`），于是启动即 `NoSuchMethodError`，并被包装成 `Could not execute entrypoint stage 'main' ... provided by 'cutthrough'`；
- 对照实验：仅移除本模组 jar，游戏完全恢复；
- 全包字节码扫描后确认冲突面共 **15 个类**（FCAP 10 个 config 类 + bus 3 个 + `Dist` + `Mod`），另有 12 个 FCAP 下游模组与 9 个 bus/Dist 下游模组处于「未爆弹」状态。

因此改为**方案 F：彻底删除垫片，加载器层用 Fabric 原生 API 重写**，使 jar 内 `net/neoforged/**` 条目归零。实测冲突类从 15 → **0**。

### 4.1 注册：`BDRegistry`（模组自有）

`DeferredRegister` 的「先排队、后统一注册」语义被保留为模组自有的 `registry.BDRegistry`，内部直接调用原版 `Registry.register`：

1. **实例化阶段**：按 `PHASE_FLUID(0) → BLOCK(1) → DATA_COMPONENT(2) → ITEM(3) → BLOCK_ENTITY(4) → TAB(5)` 顺序调用条目工厂；
2. **写注册表阶段**：按同一顺序写表。

保留两阶段不是照搬，而是因为上游存在**真实的循环依赖**：`LiquidBlock` 的构造器需要 `FlowingFluid` 实例，而流体方块物品又需要方块实例；`BDFluids` 用 `propsRef[0]` 先占位、注册流体时再回填。`BDHolder` / `BDItemHolder` / `BDBlockHolder`（后者实现 `ItemLike`）替代 `DeferredHolder` / `DeferredItem` / `DeferredBlock`。

菜单类型不再需要延迟：`BDRegistry.registerMenu(name, Ctor::new)` 直接构造 `ExtendedMenuType<T, byte[]>` 并注册，14 个菜单类的 `X_MENU.get()` 全部收敛为 `X_MENU`。

### 4.2 事件：直连 Fabric 回调

删除 `IEventBus` / `@SubscribeEvent` / `@EventBusSubscriber` / `NeoForge.EVENT_BUS`，入口点按上游阶段顺序**直接调用**：

```
BeyondDimensionsFabric.onInitialize()
  ├─ BeyondDimensions.init()        // 配置 → 排队注册 → BDRegistry.flush() → commonSetup()
  ├─ *BlockEntity.registerCapability()   // 能力登记
  ├─ BDPackets.register()
  ├─ ServerLifecycleEvents.SERVER_STARTING / SERVER_STARTED / SERVER_STOPPED
  └─ CommandRegistrationCallback.EVENT

BeyondDimensionsFabricClient.onInitializeClient()
  ├─ BeyondDimensionsClient.initClient()  // 屏幕 / 按键 / 流体模型 / 集成模块
  ├─ ClientCommandRegistrationCallback.EVENT
  └─ ClientTickEvents.END_CLIENT_TICK
```

`@Mod` / `Dist` / `FMLEnvironment` / `ModList` / `FMLCommonSetupEvent` / `FMLClientSetupEvent` 等全部由 `fabric.mod.json` 入口点声明、`EnvType`、`FabricLoader` 与上述回调取代。

### 4.3 能力：Fabric lookup

不再自建能力注册中心，直接以 Fabric 官方 lookup 作为容器：

- `item_handler/block`、`fluid_handler/block`、`energy_handler/block` → `BlockApiLookup.get(id, Class, Direction.class)`；
- `item_handler/item`、`fluid_handler/item`、`energy_handler/item` → `ItemApiLookup.get(id, Class, ItemAccess.class)`；
- 方块实体通过 `BDCapabilities.registerBlockEntity(lookup, type, provider)` 登记（4 个方块实体类，覆盖「按 `CapabilityHelper.BlockCapabilityMap` 动态注册」与「直接注册能量/物品」两种上游写法）；
- 查询统一走 `BDCapabilityAccess.getBlock/getItem/getEntity`（17 处调用点），解析顺序为「模组 lookup → Fabric `ItemStorage`/`FluidStorage` 回退」；
- 跨模组互操作仍靠回退层：`ItemStorageAdapter` / `FluidStorageAdapter` 把 Fabric 的 `Storage<ItemVariant>` / `Storage<FluidVariant>` 适配成上游的 `ResourceHandler<ItemResource>` / `ResourceHandler<FluidResource>`，`TransactionBridge` 负责事务语义对齐（NeoForge 事务提交时才提交对应的 Fabric 外层事务）；
- 实体物品能力：Fabric 无实体 lookup，玩家背包用 `PlayerInventoryStorage` 包装顶替。

### 4.4 transfer API / 流体：自有领域实现

NeoForge 26.x 的 `ResourceHandler` / `Transaction` / `SnapshotJournal` / `TransferPreconditions` 本就源自 Fabric Transfer API。它们**不是垫片**，而是本模组的领域实现，故整体迁到模组命名空间：`api.transfer.*`（15 类）+ `api.fluid.*`（3 类，含自建 `FluidStack`、`FluidType`、`BaseFlowingFluid`——26.3 原版 `FlowingFluid` 已删除 `Source` / `Flowing` 内部类，按原版水/岩浆写法补回）。

### 4.5 网络 / 菜单 / 配置 / 环境

- **网络**：`fabric.BDNetworking.playBidirectional(type, codec, serverHandler, clientHandler)` 内部调 `PayloadTypeRegistry.serverboundPlay()/clientboundPlay()` + `ServerPlayNetworking.registerGlobalReceiver`，客户端接收器隔离在仅物理客户端加载的 `BDNetworkingClient`。17 个包类的 `handle(packet, ctx)`（内含 `context.flow()` 分支）拆成 `handleServer` / `handleClient`，上下文换成模组自有的 `api.network.BDNetContext`（`player()` + `enqueueWork()`）。
- **菜单**：上游 14 个菜单都用「打开界面时附带一段额外字节」的写法，Fabric 侧用 `ExtendedMenuType<T, byte[]>` + 自定义 `byte[]` codec 复现（`BDRegistry.registerMenu`），调用点 `player.openMenu(provider[, pos|writer])` 统一走 `BDMenuOpener.open(...)`。
- **配置**：`config.BDConfigSpec`（`define/defineInRange/defineEnum/comment/build` + 值对象 `get/set/save`）以 JSON 落到 `config/beyonddimensions-<type>.json`；`Config.register()` 构造即装载并直接刷新运行时快照，不再经由事件总线。
- **杂项替换**：`Tags.Fluids.*` → `util.BDTags`；`CommonHooks.setCraftingPlayer` → `util.CraftingPlayerHooks`（线程局部量）；`CreativeModeTabRegistry` → `util.BDCreativeTabs`；`ServerLifecycleHooks` → `util.BDServerHooks`；`ClientHooks.gatherTooltipComponents` → `client.util.TooltipHelper`；`ClientTooltipFlag` → `client.util.BDTooltipFlag`；`IMenuTypeExtension` 由 `BDRegistry.registerMenu` 取代后直接删除。
- **访问权限**：上游 `accesstransformer.cfg` 的 13 条改写为 Fabric Access Widener（`beyonddimensions.accesswidener`，`official` 命名空间），另加垫片自用条目（见 §5.2）。

## 5. 26.1 → 26.3 原版 API 差分（实测清单）

### 5.1 方法/字段变动

| # | 26.1 写法 | 26.3 现状 | 处理 |

### 5.2 资源与模型

1. **NeoForge 动态流体容器模型**：`assets/beyonddimensions/items/xp_fluid_bucket.json` 原用 `neoforge:fluid_container` 模型加载器，Fabric 无等价物（客户端报 `Unknown element id: neoforge:fluid_container`）。本次改为静态 `minecraft:item/generated` + **新绘制的 `item/xp_fluid_bucket.png`**（从原版桶贴图程序化着色为经验流体绿）。**功能不受影响，但桶内流体不会随装填量变化**。
2. **中文文件名资源**：`textures/gui/sprites/widget/漏斗{允许,图,禁止}.png` 三个纹理被 Fabric 资源包校验拒绝（`Invalid path ... ignoring`）。这三个文件在代码里**没有任何引用**，已重命名为 `hopper_allow/hopper_icon/hopper_deny.png`。
3. **客户端流体渲染**：26.3 原版 `FluidStateModelSet.bake` 只烘培水与岩浆，新增客户端 Mixin `FluidStateModelSetMixin` 在返回处补入本模组登记的流体模型（对应上游的 `RegisterFluidModelsEvent`）。

### 7.3 未验证 / 已知缺口

1. **存储网络的实机玩法**：创建网络需要玩家上下文（`/bdtools network create <player>`），无头服务器无玩家；网络的分化存储、UI 页面交互、合成菜单、网络通道/泵/漏斗/熔炉的实际搬运逻辑**未经真人操作验证**。建议后续用真人客户端连本机服务器做一轮验收。
2. **GUI 观感**：终端/控制/熔炉等 14 个界面已编译、已注册屏幕与按键，但未做视觉走查；`DimensionsNetGUI` 的滚动、排序、搜索等交互未验证。
3. **流体渲染细节**：桶外观为静态贴图（§5.2）；流体方块在世界中的贴图依赖 `FluidStateModelSetMixin`（现读取模组自有登记表 `BDFluidModels`），仅做了"模型能烘培、无报错"级别的验证。

5. **集成模块**：见 §3.2，全部延后。
6. **实体能力**：Fabric 无实体 lookup API，`BDCapabilities.Item.ENTITY` 只对玩家生效（用 `PlayerInventoryStorage` 包装），非玩家实体返回 `null`——与上游「非玩家实体可能由其他模组提供该能力」的行为存在差异。

## 8. 后续建议（按性价比排序）

1. **真人客户端验收**：连本机 Fabric 26.3 服务器，跑一遍「合成维度创造器 → 建网络 → 开存储界面 → 放/取物品 → 接口/通道搬运」。
2. **在 140 模组整合包中回归**：本产物已消除全部类遮蔽，但仍建议在真实整合包中跑一轮进入世界 + 开界面，确认与其他 21 个引用 `net.neoforged` 的模组共存无异常。
3. **补 RS / JEI 集成**：两者都有 Fabric 版本，但 API 与 NeoForge 版差异较大，建议按模块单独排期；Curios 在 Fabric 侧对应的是 Trinkets/Accessories，需要重写挂载层。
4. **动态流体桶模型**：用 Fabric 的 `ModelLoadingPlugin` + 自定义 `UnbakedModel` 复刻 `neoforge:fluid_container`。
5. **datagen 恢复**：用 Fabric 的 datagen API（`fabric-data-generation-api-v1`）重写 10 个 provider，即可恢复数据生成流程。
6. **`FuelHelper` 精化**：构造最小 `LootContext` 以精确解析 `CookingFuel.burnTime`。
7. **`BDScreens` 的 `MenuScreens.register` 依赖 AW**：26.3 把该方法收成 private，当前靠 Access Widener 打开；若后续版本改变可见性，需要同步维护 AW 条目。
